# 第 1 部分：基础与工作流

<a id="ch1"></a>
## 第 1 章 核心理念：为什么团队负责人不单干？

插件是一个调度器。它并不强迫神经网络闲聊，而是为此创造条件。

* **团队负责人（Team Lead / Lead）** —— 一个待在聊天窗口里的普通智能体。如果你只跟它说「做个项目」，它会像独行侠一样自己把活全干了。
* **插件** —— 一层强制启用角色（产品经理、架构师、QA 等）的扩展，让它们通过 **会议** 沟通、通过 **任务板** 执行任务。
* **你（人类）** —— 总监。你设定目标、创建会议、检查文档并点击「确认」。

---

<a id="ch2"></a>
## 第 2 章 版本生命周期（流水线）

项目始终沿这条链路推进：

`需求` ➡️ `架构` ➡️ `开发` ➡️ `评审` ➡️ `测试` ➡️ `完成`

每个阶段都设有 **关卡（Gate）**。在该阶段的条件达成之前，通往下一步的按钮会保持不可用（置灰）。

1. **需求：** 需要创建一次会议并确认需求文档。
2. **架构：** 架构师必须召开会议并撰写架构文档（由你确认）。
3. **开发：** 插件为开发者创建任务（例如 Zoe 和 Owen）。你等待任务完成。
4. **评审与测试：** 智能体撰写报告。你检查并确认这些报告。

---

<a id="ch3"></a>
## 第 3 章 用户界面（该点哪里）

* **版本看板：** 主界面。这里可以看到各阶段、活跃任务、团队负载（谁手上多少任务）以及 **产物**（文档）。右下角是「手动确认」区块，报告确认按钮会在那里出现。
* **需求：** 想法清单。从这里创建新需求，并发起首轮需求澄清会议。
* **会议：** 协商会议室。在这里选择参与者、提出问题，并命令主持人生成最终文档。
* **设置：** 在这里绑定团队、配置角色（提示词）与模型，以及删除版本（在「版本设置」窗口中）。

---

<a id="ch4"></a>
## 第 4 章 实操示例（迷你项目「待办清单」）

用一个测试项目（待办清单 To-Do List）的分步场景来熟悉工作流：

1. 创建一个 **新版本** `v0.2.0-todo`。
2. 进入 **需求** 选项卡 ➡️ 点击 **+ 新建需求**。
   - **标题：** `待办清单（To-Do）`。
   - **描述：** `用于添加、删除及标记任务完成的 Web 应用。设计：极简风格，一个输入框和一个「添加」按钮。`
   - **执行人：** 勾选一名开发者（例如 `Zoe`）。
3. 点击 **「创建需求澄清会议」**。
4. 进入 **会议** 选项卡 ➡️ 点击 **「开始会议」**。
5. 向执行人提问：*「你建议采用怎样的组件结构？」*（等待回答）。
6. 点击 **「请主持人准备文档」** ➡️ 保存需求。
7. 点击 **「结束并生成会议纪要」**。
8. 回到 **版本看板** ➡️ 确认产物（需求文档）。
9. 点击 **「进入架构阶段」** ➡️ 与架构师（例如 `Kael`）开会 ➡️ 结束会议 ➡️ 确认架构文档。
10. 点击 **「开始开发」** ➡️ 等待开发者完成任务。
11. 在右下角点击 **「确认并进入评审」**。
12. 等待评审人的报告（或手动录入）➡️ 确认。
13. 等待 QA 的测试报告（例如 `Mia`）➡️ 确认 ➡️ **版本完成！**

<a id="ch5"></a>
## 第 5 章 情景推演（如果……会怎样）

### 1. 在空会议上点击「结束并生成会议纪要」会怎样？
**结果：** 会议会关闭，纪要会生成，但内容为空。你仍然需要手动创建或编辑需求文档，才能通过关卡。

### 2. 智能体报出 `ARTIFACT_PARSE_FAILED` 错误会怎样？
**结果：** 模型忘了加上隐藏的标记符。再点一次生成按钮；如果仍不行，就手动编辑产物——插件只关心其中的文本内容。

### 3. 任务卡在「进行中」已经 20 分钟会怎样？
**结果：** 智能体卡住或陷入循环。查看左侧面板：如果那里亮着黄色圆点「等待回复」，就进入聊天回答智能体的问题；如果没有圆点，打开它的聊天窗口输入：*「结束任务并汇报」*。也可以直接强制点击「确认开发」。

### 4. 如何删除版本？
**结果：** 只能删除 `draft`（草稿）状态的版本。进入 **版本设置**（名称旁边的按钮）➡️ 点击窗口左下角的 **「删除」**。`active` 或 `completed` 状态的版本无法删除，只能归档。

### 5. 把需求从版本里解绑会怎样？
**结果：** 需求会回到总列表，「删除」按钮重新可用。但为该需求在此版本内创建的所有文档，仍会留在该版本的产物中。

### 6. 「高效模式」是做什么的？
**结果：** 如果在设置中启用该选项，智能体只在非工作时段执行任务（按北京时间 `UTC+8`：夜间与周末）。白天任务会停留在「等待」状态。

> **时区说明：** 高效模式是针对中国市场及 DeepSeek 服务器负载曲线设计的。如果你位于其他时区，需要自行换算触发窗口（例如莫斯科 `UTC+3`，北京的非工作时段对应莫斯科的傍晚、夜间和清晨）。未来插件版本中，如有需要可在 `index.js` 文件里调整这段逻辑。

## 第 6 章 维护与备份

* 项目根目录下有一个隐藏文件夹 `.dsh_teams`，里面是 `planner/state.json` 文件。
* 若想保留版本、会议与产物的历史记录，切勿删除该文件夹。
* 为防止数据丢失，请定期把 `.dsh_teams` 文件夹复制到备份存储。
* 从 GitHub 更新插件时，本地代码改动（例如 `lib/client.js` 里的自定义按钮）可能被覆盖。务必单独留存改动过的文件，或使用 Git 分支管理。

# 第 2 部分：安装、架构与更新

<a id="ch7"></a>
## 第 7 章 版本兼容性（须知事项）

插件不是独立程序，而是架在 DeepSeek Harness（DSH）内核之上的扩展。

* **DSH 版本：** 插件 `v0.9.1` 适配 DSH 内核 `0.2.1-rc.2` 及以上（直到 `0.3.0`）。当 DSH 升级到全局版本 `0.3.0` 时，在相应补丁发布前，插件可能失去兼容性。
* **运行环境：** 需要安装 **Node.js 20+**。
* **配置文件：** DSH 设置中必须启用实验性的 **Agent Teams** 配置，否则插件看不到团队成员列表。

---

<a id="ch8"></a>
## 第 8 章 从零安装插件

插件不会自动从外部注册表加载——必须放到本地磁盘上并关联到 DSH。

### 方案 A：自动安装（随附脚本）
插件仓库根目录的 `scripts` 文件夹中有 `install-manual.ps1` 脚本，运行后会自动完成所有步骤：
1. 备份 DSH 配置（通常是 `web` 文件夹）。
2. 通过 `link:` 将插件加入依赖。
3. 在 DSH 构建系统中注册插件。

### 方案 B：手动安装（通过 `cordis.patch.yml`）
DSH 使用插件配置文件（清单）。插件会把 `cordis.patch.yml` 中的如下区块加进去：

```yaml
- insert:
    - id: agent-team-planner
      name: dsh-agent-team-planner
```

这条记录指示 DSH 内核在启动时加载 `dsh-agent-team-planner`。如果你重命名了插件文件夹，必须同步更新清单里的名称，否则 DSH 找不到它。

---

<a id="ch9"></a>
## 第 9 章 修改代码后如何正确重启 DSH

插件分为两个相互独立的部分：
* **后端（`lib/index.js`）：** 运行在 Node.js 服务端。
* **前端（`lib/client.js`）：** 在浏览器窗口中执行。

**改动生效规则：**
1. **修改的是 `lib/client.js`（界面）：** 无需重启 DSH 服务。在浏览器中按 `Ctrl + F5` 强制刷新页面，清除 `.js` 文件缓存即可。
2. **修改的是 `lib/index.js`（服务端逻辑）：** 必须在终端里完全停止 DSH 进程并重新启动，让 Node.js 重新读取文件。

<a id="ch10"></a>
## 第 10 章 从 GitHub 更新且不丢失自定义改动

如果你改过插件的本地代码，`git pull` 可能引发冲突或覆盖你的改动。

### 方法 1：手动搬运
1. 把改动过的 `lib/client.js` 复制到一个单独的备份文件夹。
2. 在终端执行：
   ```bash
   git pull origin main
   ```
3. 打开备份的文件，手动把你的改动迁移到更新后的代码中。

### 方法 2：用独立 Git 分支（推荐）
为本地改动建一个自己的分支：

```bash
git checkout -b my-custom-features
```

在该分支上用提交记录你的改动。需要从主仓库拉取更新时执行：

```bash
git checkout main
git pull
git checkout my-custom-features
git rebase main
```

<a id="ch11"></a>
## 第 11 章 故障排查：插件加载失败怎么办

如果重启 DSH 后，插件图标从左侧面板消失了：

1. **查看 DSH 终端日志。** 出现提及 `agent-team-planner` 的红色信息，说明初始化出错（例如手动改动后产生的语法错误）。
2. **检查 `client.js` 语法。** 确认没有漏掉闭合括号或逗号。
3. **检查插件在界面中的状态。** 打开 DSH 配置设置（插件菜单），确认 `dsh-agent-team-planner` 开关处于 **「已启用」**。
4. **检查内核版本。** 确认 DSH 版本符合第 7 章的兼容性要求。

# 第 3 部分：高级角色配置与任务适配

<a id="ch12"></a>
## 第 12 章 提示词如何生效，以及如何让智能体用俄语写作

插件采用三级提示词体系（从通用规则到具体规则）：

1. **角色（Role）：** 基础专业分工（例如「产品经理」包含需求收集与验收标准的指令）。
2. **成员提示词（Member Prompt）：** 针对具体智能体的个性化指令（例如让一个产品经理「回答要简洁」，让另一个「展开详述」）。
3. **自定义要求（Custom Prompt）：** 针对项目或团队的附加规则。

> **本地化提示：** 若希望智能体始终用俄语对话并撰写文档，打开 **设置** ➡️ **角色与提示词**，选中对应角色，在基础提示词末尾加上一行：  
> *«ВАЖНО: Общайся, думай и пиши все документы строго на русском языке»*  
> （中文释义：重要：请严格用俄语交流、思考并撰写所有文档。）  
> 随后点击 **「将提示词应用到成员」**。

<a id="ch13"></a>
## 第 13 章 适配非 IT 任务（CAD 图纸、设计、文案）

插件架构是通用的：「架构」和「开发」两个阶段适用于任何结构化任务。

### 示例：为工程图纸（CAD / 3D）配置团队
1. 进入 **设置** ➡️ **角色与提示词** ➡️ 点击 **+ 新建角色**。
2. 创建专门的角色：
   - **总工程师（Chief Engineer）：** *「你负责设计技术系统。你的任务是计算载荷、选择材料并编制物料清单（规格明细表）。」*
   - **绘图员（Draftsman）：** *「你负责生成 SVG 格式的图纸，或编写供 CadQuery / FreeCAD 库使用的 Python 代码。」*
   - **检验员（Inspector）：** *「你负责检查图纸与规格明细表是否符合 GOST（ГОСТ）标准及安全要求。」*
3. 由于语言模型无法直接生成二进制 `.dwg` 文件，请用文本格式来表述需求：*「以 SVG 文件形式创建零件图纸」* 或 *「编写生成 3D 模型的 Python 脚本」*。
4. 在 **设置** ➡️ **成员** 选项卡中创建成员，并把新角色绑定给他们。

<a id="ch14"></a>
## 第 14 章 模型分配（智能预算管理）

为不同角色指定不同的语言模型，可以优化预算与工作速度：

* **架构师 / 总工程师：** 需要深度分析与风险推演，最适合用推理型模型（例如 `DeepSeek-R1` 或更高阶的 `Pro` 版本）。
* **前端 / 后端 / 绘图员：** 适合标准通用模型（`DeepSeek-V4` / `DeepSeek-Chat`），在成本与代码生成质量之间取得平衡。
* **QA / 测试 / 评审：** 按清单核对的工作适合更快、更省的模型（例如 `Flash` 或 `Lite` 版本）。

**如何指定模型：**
1. 打开 **设置** ➡️ **成员**，点击目标智能体旁的 **「编辑」**。
2. 在 **「模型路由」（Model route）** 区块中选择服务商与具体模型。
3. 点击 **「保存」**。新模型会在该智能体下次启动时生效。

---

<a id="ch15"></a>
## 第 15 章 Token 限额与后备模型

`Agent Team Planner` 插件只充当任务调度器——它向 DSH 内核下达「用选定模型启动某个智能体」的指令，但并不直接管理 Token 限额。

* **Token 限额：** 在 DSH 内核层面全局配置（服务商配置或 `.env` 环境变量）。可在那里设置最大回复长度（`max_tokens`），避免智能体白白消耗预算。
* **后备模型（Fallback）：** API 故障时的服务商切换由 DSH 自身的路由配置负责。在插件内部，你可以通过给不同成员分配不同服务商的模型，来降低停工风险。

---

<a id="ch16"></a>
## 第 16 章 如何禁止智能体写代码（设计与内容项目适用）

处理文本、文档或设计概念时，智能体默认可能试图创建项目文件或安装依赖包。要避免这一点：

1. 打开 **设置** ➡️ **角色与提示词** ➡️ **团队负责人**。
2. 把基础提示词中关于开发的段落替换为硬性限制：  
   *「禁止编写程序代码、禁止执行控制台命令。你的任务是协调文本与设计材料的准备。请按如下格式下达任务：『撰写第 1 章』『准备版式结构』。」*
3. 在需求文本中明确写出期望的产出格式（例如：*「不要写代码。最终产物为 Markdown 文档」*）。

# 第 4 部分：权限、沙箱与并行执行

<a id="ch17"></a>
## 第 17 章 DSH 安全架构：为何不只是「沙箱」

DSH 中操作执行的安全性建立在三个相互独立的层级上：

1. **沙箱模式（Sandbox Mode）：** 界定智能体访问文件系统的边界。
2. **审批策略（Approval Policy）：** 规定智能体在执行命令前必须向用户请求许可的情形。
3. **工作区隔离：** 规定多个智能体共享同一目录时的访问规则。

---

<a id="ch18"></a>
## 第 18 章 沙箱模式

DSH 支持三种主要的文件系统工作模式：

* **`read-only`（只读）：** 禁止任何文件修改。适用于只需查看代码或文档的分析师、评审人和测试人员。
* **`workspace-write`（写入工作区）：** 仅允许在当前项目目录内创建和修改文件，超出工作文件夹即被拦截。这是开发者与架构师推荐的默认模式。
* **`danger-full-access`（完全访问）：** 彻底关闭沙箱限制，智能体可访问整个文件系统和系统命令。仅在需要安装全局依赖、且环境可信时使用。

> **Windows 注意事项：** 在 Windows 环境下，操作系统层面的 `read-only` 模式存在技术限制，启动子进程时并不总能保证完全阻断写入。请勿把它当作保护关键系统文件的唯一手段。

---

<a id="ch19"></a>
## 第 19 章 审批策略

审批策略决定智能体执行潜在危险操作（例如在终端运行脚本）时的自主程度：

* **`ask`（询问）：** 执行命令前，智能体会暂停工作，等待用户在 DSH 界面中手动确认。
* **`never`（从不询问）：** 智能体不向用户请求确认。视 DSH 配置而定，这既可能允许沙箱内的操作自动执行，也可能自动拒绝需要提权的操作。

实践中，`workspace-write` + `ask` 的组合能在工作效率与安全管控之间取得最佳平衡。

---

<a id="ch20"></a>
## 第 20 章 文件隔离：防止智能体互相覆盖

当两名开发者（例如 `Zoe` 和 `Owen`）并行编辑同一项目文件夹里的文件时，可能出现竞态条件（race condition），导致彼此覆盖改动。

### DSH 内置机制
标准 *Agent Teams* 框架为所有成员使用同一个共享工作目录。为做区分，会采用 **写入范围（write scopes）**——即提示词中说明「哪些文件归哪个智能体负责」的文字性建议。由于这属于软性约束，同时修改公共模块时仍可能产生冲突。

### 解决方案
1. **手动拆分任务与目录（基础方法）：** 在派活阶段就明确给每个智能体分配互不重叠的文件或子目录（例如一人只负责 `src/components/`，另一人负责 `src/utils/`）。
2. **使用文件锁或分支类插件：** DSH 生态中有专门的文件锁扩展（`dsh-file-claim`），或通过 `git worktree` 做隔离的扩展（`dsh-plugin-worktrees`），可把智能体的工作分散到不同的工作副本，之后再合并分支 *（见附录）*。

---

<a id="ch21"></a>
## 第 21 章 最佳实践：配置角色权限

典型团队的推荐权限矩阵：

| 智能体角色 | 沙箱模式（Sandbox） | 审批策略（Approval） | 理由 |
| :--- | :--- | :--- | :--- |
| **测试（QA）** | `read-only` | `ask` | 阅读代码、核对逻辑，无需写入项目文件。 |
| **评审（Code Review）** | `read-only` | `ask` | 分析改动，但无权直接编辑。 |
| **架构师** | `workspace-write` | `ask` | 在工作文件夹内创建和更新项目文档。 |
| **开发者** | `workspace-write` | `ask` | 在用户管控下，严格在项目目录内写代码。 |
| **DevOps / 工程师** | `danger-full-access` | `ask` | 可能需要访问系统工具，但 `ask` 对管控命令必不可少。 |

权限可在 DSH 配置参数中设置，或在界面里通过 `/permission` 命令配置。避免默认给所有成员分配 `danger-full-access`。

# 第 5 部分：高级场景与灾难恢复

<a id="ch22"></a>
## 第 22 章 断网或 API 服务商故障

如果网络断开或 API 服务器暂时不可用，界面中的任务可能卡在 `in_progress` 状态，日志里会出现网络错误。

**处理步骤：**
1. **不必慌：** 调度器会把所有状态与产物保存在本地磁盘上，数据不会丢。
2. 等待连接恢复或 API 稳定。
3. 刷新插件页面（`F5`）。
4. 如果智能体没有自动恢复，打开它的私聊窗口发送：*「继续执行当前任务」*。
5. 如果任务彻底卡死、但主要工作已完成，可以用「手动确认」区块里的 **「确认」** 按钮强制结束该阶段。

---

<a id="ch23"></a>
## 第 23 章 API 余额耗尽或触发 Token 速率限制

服务商余额用尽或达到请求上限时，DSH 日志中会出现 `429 Too Many Requests` 或 `Insufficient Balance` 错误。

**处理步骤：**
1. 在服务商后台充值（或等待请求限额重置）。
2. 无需重启 DSH 服务——回到 **版本看板** 即可。
3. 打开停下来的智能体聊天窗口，输入：*「余额已充值，继续工作」*。
4. 如果任务仍处于阻塞状态，通过确认按钮手动结束该阶段，把流水线推进到下一步。
5. **检查运行模式：** 若任务不启动、但日志里又没有 API 报错，请确认没有开启「高效模式」——它会把任务压到北京时间夜间才执行（见第 5 章）。

---

<a id="ch24"></a>
## 第 24 章 手动回滚：编辑 state.json（时光机）

插件会在每次重要操作后自动创建状态快照。如果需要撤销误操作（例如误确认了空产物），可以手动回滚。

**文件位置：**
* 当前状态：`[项目文件夹]/.dsh_teams/planner/state.json`
* 备份：`[项目文件夹]/.dsh_teams/planner/backups/`（保留最近 10 个快照，形如 `state-17123456789.json`）。

**回滚分步说明：**
1. **完全关闭 DSH**，避免服务端在你编辑期间覆写文件。
2. 把当前的 `state.json` 另存一份到单独的文件夹。
3. 在 `backups` 文件夹里找到出错之前时间戳对应的文件。
4. 把选中的文件复制到 `planner/` 目录，并重命名为 `state.json`（覆盖原文件）。
5. 用文本编辑器打开新的 `state.json`，在开头找到 `"revision": X` 参数，并 **把这个数字加 1**（例如把 `"revision": 12` 改成 `"revision": 13`）。前端要靠它识别数据已更新。
6. 启动 DSH。

> ⚠️ **JSON 语法警告：** 编辑时务必极其小心。JSON 不容忍语法错误（多余或缺失的逗号、引号、括号）。如果启动后插件报状态读取错误（`STATE_CORRUPT`），说明文件结构已被破坏——关闭 DSH，用你备份的原始 `state.json` 恢复。

---

<a id="ch25"></a>
## 第 25 章 完全重置（终极手段）

如果项目里堆积了太多重复需求或卡死状态，从头开始规划反而更省事：

1. 完全关闭 DSH。
2. 删除项目根目录下的 `.dsh_teams` 文件夹（或将其重命名为 `.dsh_teams_backup` 留作归档）。
3. 重新启动 DSH。插件会自动初始化一块干净的版本看板。

*（注：智能体在项目工作目录中写下的所有源代码都不会受影响——被删除的只是调度器自身的任务、会议与产物历史。）*

# 附录

## 附录 配套插件术语表

以下是 **DeepSeek Harness（DSH）** 生态中可与 `dsh-agent-team-planner` 配合使用的工具与扩展：

* **`dsh-agent-teams`** —— DSH 中团队协作的基础框架，负责创建智能体配置、分配角色以及智能体之间的消息交换，是调度器运行的必要基础。
* **`dsh-agent-team-gui`** —— 智能体团队的可视化管理界面，可直观查看成员状态，并通过图形面板与其交互。
* **`dsh-file-claim`** —— 多智能体并行时协调文件访问的扩展。它引入预锁定机制（对文件「申领」），防止两名开发者同时工作导致代码被覆盖。
* **`dsh-plugin-worktrees`** —— 基于 `git worktree` 的工作区隔离工具。为每个并行任务分配独立的物理目录和 Git 分支，把文件冲突推迟到合并改动阶段才处理。

> **说明：** `dsh-file-claim` 与 `dsh-plugin-worktrees` 是作为生态中的概念性架构方案列出的。安装前请在 DSH 官方插件管理器或 GitHub 上核实其是否存在及最新名称。如果注册表里没有合适的包，请采用在智能体之间手动拆分文件与目录的方法（见第 20 章）。
